# Reflection #5

Pod Members: **Monika Basnet, Ava Flanigan, & Jennifer Ye**

## AI Feature Retrospective — "How we built it"

Our AI feature is the **Need Prioritization & Explanation Engine**: the volunteer/org triage feed ranks open requests and, for each one, shows a one- or two-sentence reason it ranks where it does.

**How closely did the shipped behavior match the Week 6 spec?** The *shape* held up well; the *internals* drifted. What matched: Cohere embeddings (`embed-english-light-v3.0`), `explainer.js` by name, in-app cosine similarity, the time-decay + cluster-density scoring signals, and server-side-only execution. What changed:

- **No real clustering.** The spec output `clusterId` and a debug `signals` object. We never built true clustering — the *count* of similar nearby requests became the density proxy — so we dropped `clusterId` from the spec. `signals` we said we'd add (the values are computed in `scoring.js`), but the prioritizer response still returns `similarRequests`, not a `signals` object. That one is a spec promise we didn't finish landing.
- **A 4-provider text-generation chain, not Cohere.** Explanation/classification runs OpenRouter → Gemini → OpenAI (with Anthropic Claude local-only). The Week 6 spec never anticipated a fallback chain — it was written as if one provider generated the text. We added the chain in Sprint 2 for resilience and cost control across free tiers.
- **A life-safety classifier the spec never mentioned.** `lifeSafetyClassifier.js` floors priority for life-threatening requests so clustering/recency math can't out-rank them. Safety-critical behavior that emerged from using the feature, not from specifying it.
- **Graceful degradation works — but for a reason the spec didn't foresee.** The spec promised the feed still renders on AI failure, sorted by urgency + recency, with a "temporarily unavailable" notice. What actually protects the feed is that scoring happens at *write* time and `priorityScore`/`reasoning` are **persisted** — so a live provider outage never blanks the feed; it reads stored scores. The gap the spec was worried about landed on the *write* path instead: `POST /api/requests` and the `/api/prioritize/*` routes still return HTTP 500 on AI failure rather than degrading, so a request *created during* an outage gets no score and the create errors. We reached the spec's user-visible goal by a different mechanism than the spec described, and left a smaller, more precise gap behind.

**What we'd change about the spec if starting over.** The input/output contract was precise enough to build against — the JSON example and the field list were genuinely useful. The weak spots were all in the *operational* details AI behavior actually hinges on: we never said which provider generated the text or that there'd be a fallback chain, we specified `clusterId` for clustering we hadn't committed to building, and we listed "local resource coverage" as an input signal that never made it into the score. If we started over we'd specify the provider strategy and the exact failure behavior *per code path* (read vs. write) up front, and we'd only put fields in the output contract that we were sure we'd compute.

**What we learned about specifying AI behavior vs. system behavior.** For deterministic system behavior, the spec is a contract you can assert against. For AI, the input/output *shape* is still a hard contract, but the *content* isn't — so the parts of the spec that earned their keep were the **validation criteria** ("valid numeric score 0–100," "reasoning tied to a real signal," "no fabricated facts," "1–2 sentences") and the **fallback plan**, because those are the only parts you can test when the exact wording changes every call. The clustering and provider details, by contrast, were the parts most likely to drift, because they were implementation guesses dressed up as spec. Our takeaway: for AI, spec the *bounds and the failure mode*, not the *mechanism*.

**A hypothetical second AI feature.** A **volunteer↔request matcher** — given a volunteer's skills, availability, and location, suggest the requests where they'd have the most impact. Knowing what we know now, the spec would lead with the validation criteria and a hard output contract (`requestId`, `matchScore` 0–100, `reasoning`, and an explicit "no confident match" response), name the provider + fallback path from day one, and specify the failure behavior separately for the read and write paths — the three things our first AI spec left implicit and paid for later.

## Reflection Questions

* How was the pacing of the capstone project — too slow, just right, or too fast?

Mostly just right, but front-loaded. Sprint 1 ran *ahead* of plan — we built the org/volunteer workflow, i18n, geocoding, and crisis-event ingestion before they were scheduled — which felt great at the time and created the spec drift we spent Sprints 2 and 3 paying down. The middle sprints were the tightest: real testing under deadline pressure while still landing features (the Deepgram voice intake alone took several passes). If the pace had a flaw it wasn't total speed, it was that early over-delivery borrowed time from later documentation and hardening.

* To what extent did your plan change over the course of development? Knowing what you know now, what would you do differently if you were starting over?

A lot changed, and the reconciliation section documents it honestly: we dropped React Query and `AuthContext` entirely (plain axios + `localStorage` + a `usePolling` hook), kept `embeddingJson` as `TEXT` with in-JS cosine similarity instead of adopting pgvector, shipped a `{ success, message, data }` envelope instead of flat REST shapes, renamed `register`→`signup`, and replaced the documented `/responses` + AI `/matches` flow with an interest/assignment model (the `Match` table exists but is unused). Almost none of these were mistakes — they were reasonable calls under time pressure — but the gap between doc and code kept reopening. Starting over, we'd reconcile the spec at the *end of every sprint*, not at a mid-project audit, and we'd write the State Architecture section far more loosely up front, since prescribing a React Query + context design we never adopted made that section describe an intended app rather than the real one.

* How did the spec-driven workflow hold up across the full project? When did maintaining project_plan.md save time or prevent confusion — and when did it feel like overhead?

The Data Model and API Contracts sections were the workflow's biggest wins — concrete tables, field types, and endpoint shapes gave Claude and us something real to build against, and they stayed useful even as specifics changed. The **Decisions Log** (and AI Feature Decisions Log) paid off every time someone asked "wait, why *didn't* we use pgvector / React Query / a real matcher?" — the answer was written down instead of re-litigated. Where it felt like overhead: keeping the *narrative* sections (State Architecture especially) in sync when the code had already moved on. The honest pattern all project long was "the codebase keeps outrunning the documentation" — the spec was most valuable as a record of *decisions* and *contracts*, least valuable as a description of *current architecture*.

* Where was Claude most useful during capstone development? Where did its output require the most revision, and what was missing from the spec when that happened?

Claude was most useful where the spec was concrete: generating routes/controllers/models against the API Contracts and Data Model, writing tests, and — critically — doing the spec-audit and reconciliation passes, which is tedious to do by hand. It required the most revision on the AI feature itself, and the reason maps exactly to the spec gaps: because Week 6 never specified the provider strategy or the real failure behavior, Claude's first cuts assumed a single provider and a happy path, and we had to rework them into the fallback chain and the persisted-score degradation model. The lesson repeated itself — Claude is only as good as the precision of the spec, and the imprecise parts (provider chain, clustering, per-path failure) were exactly where its output needed the most rework.

* Looking back at the Week 6 spec vs. the final state of project_plan.md: what changed, and what stayed stable? What does the git history of your planning file tell you about how the project evolved?

**Stable:** the product intent, the core Data Model entities, the AI feature's *purpose* and validation criteria, and server-side execution of AI. **Changed:** the state stack, the vector storage approach, the response envelope, the collaboration surface (matches/responses/messaging/voting largely cut or deferred), and the AI internals (provider chain, no clustering, life-safety classifier, plus six-plus AI features the original spec never mentioned — chat assistant, voice intake, field extraction, resource advisor, task-date and task-suggestion advisors). The git history of the planning file is the tell: only a handful of commits touch it (`Initial commit`, then `update project_plan.md`, then `add sprint 2 midpoint spec reconciliation and reflection 2`, then an emoji-strip cleanup). That sparse history *is* the story — the code changed constantly, the plan changed in occasional big reconciliation batches. We documented in bursts at audit time rather than continuously, which is exactly why drift accumulated between the bursts.

* How did the AI Feature Decisions Log hold up? Was it useful to have a running record of how the AI feature changed across sprints?

It held up as the single most useful AI artifact — more than the original spec by the end. Each row captures a real turning point (OpenAI→Cohere embeddings for the free tier, the multi-provider fallback chain, `TEXT` + in-JS cosine over pgvector, dropping `clusterId` / adding `signals`, the life-safety classifier, Whisper voice intake) *with the reason attached*, which is what stopped us from re-arguing settled decisions. Its one weakness mirrors the planning file's: it was written in bursts (most rows are dated Sprint 2), so decisions made *between* audits weren't logged in real time. If we'd appended to it the day each decision was made rather than at reconciliation time, it would have been a perfect record instead of a very good one.

* How helpful were the labs and weekly assignments in preparing you for capstone work? What topics do you still have questions about?

The Week 4 endpoint-sketch template and the Week 6 AI feature spec directly seeded the capstone — we reused both structures verbatim. The risk-analysis framing (regression vs. design vs. schedule vs. documentation risk) gave us a shared vocabulary for the constant "fix it now vs. leave it" calls, especially around the fragile voice/mic code, and the two-track bug bash (functional testing + a dedicated spec-audit owner) was the most actionable single exercise — it kept spec drift from getting buried under functional bugs. Open questions: **how much E2E coverage is "enough"** for a demo without over-investing (we added Playwright tests but never felt sure), and **how to validate non-deterministic AI output systematically** beyond the bounds-and-fallback checks we wrote by hand.

* Which resources were most helpful during the capstone — mentors, pod syncs, wireframes, sprint planning, the bug bash, or something else?

The **bug bash / spec-audit** was the most valuable, because it's what forced the reconciliation that kept the whole spec-driven approach honest. **Sprint planning** and the running **pod-sync notes** were close behind — they're where the build-vs-cut decisions got made and where at-risk items (AI graceful degradation, spec accuracy for late features, voice-intake fragility) got tracked sprint to sprint. Mentor input was most useful precisely on the judgment calls where the spec couldn't help us: what to defer, what to document as a known limitation, and what not to touch this close to Demo Day.
